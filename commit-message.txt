feat(kids): add year_level field and pastor leader-assignment on create

Schema:
- Added year_level integer column to kids (7-12, nullable), with a
  check constraint. Nullable so existing kids aren't broken; they
  show as "Unassigned" until a leader sets it.

Backend (routes/kids.js):
- Added year_level to the destructured fields and insert payload in
  POST /.
- Added year_level to the destructured fields and update payload in
  PUT /:id.
- No changes needed in leaders.js: POST /:leaderId/kids and
  PUT /leaders/kids/:kidId already pass req.body through unfiltered,
  so year_level (and any other KidForm field) flows through
  automatically for pastor-initiated create/edit.

Frontend (KidForm.jsx):
- Added a Year Level select (7-12, "Unassigned" default).
- Removed the showExtendedFields gating entirely. status_code,
  parentname, address, baptised, and sunday_regulars now render
  unconditionally instead of being hidden depending on which screen
  opened the form. This was the root cause of AddKids.jsx (leader's
  own quick-add) missing fields that KidManagement's edit flow had.

Frontend (AddKids.jsx):
- Replaced the standalone implementation (separate formData shape,
  duplicated validation, duplicated checkbox markup) with a thin
  wrapper around KidForm, matching the pattern AddKidModal.jsx
  already used. Removes ~70 lines of duplicated logic and the
  parentPhone/parent_phone, yearLevel/year_level naming mismatches
  that came with maintaining two form implementations.

Frontend (AddKidModal.jsx):
- Added an optional requireLeaderSelection prop. When true, renders
  a "Assign to Leader" dropdown (populated via getLeaders()) above
  the form and requires a selection before submit; onAdded is then
  called as onAdded(formData, selectedLeaderId) instead of
  onAdded(formData). Defaults to false, so KidsList.jsx's existing
  usage (leader adding their own kid) is unaffected.

Frontend (AllKidsList.jsx):
- handleAddKid now calls createKidForLeader(leaderId, ...) instead
  of createKid(...), routing pastor-created kids through
  POST /leaders/:leaderId/kids (existing route, already does pastor
  + getManagedLeaderIds verification) instead of POST /kids, which
  would have silently attributed the kid to the pastor instead of
  the selected leader.
- AddKidModal is rendered with requireLeaderSelection={true}.
- Swapped a stray alert() for toast.error() in the catch block to
  match the rest of the file's error-handling convention.

Notes:
- AddKidModal's onAdded signature now differs based on
  requireLeaderSelection (1 arg vs 2). Not type-enforced; worth
  remembering if a third caller is added later.
- Confirmed AllKidsList is only reachable via a pastor-gated route,
  and POST /:leaderId/kids independently enforces pastor role
  server-side, so there's no gap even if frontend routing were
  bypassed.
